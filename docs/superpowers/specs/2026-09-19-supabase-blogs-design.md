# Supabase Database Wireup — Blogs & Blog Posts

Date: 2026-09-19

## Goal

Wire up Supabase as the app's Postgres database, accessed server-side through Prisma, with two tables: `blogs` and `blog_posts`.

## Access Pattern

All reads/writes go through Next.js server-side code (API routes / `getServerSideProps`) using Prisma with a direct Postgres connection to Supabase. No public Supabase client is used from the browser, so Row Level Security is not required — Prisma connects directly to Postgres, bypassing PostgREST.

## Dependencies

- `prisma` (dev dependency, CLI)
- `@prisma/client` (runtime)

## Files

- `prisma/schema.prisma` — datasource + models (below).
- `lib/prisma.ts` — singleton `PrismaClient` instance, cached on `globalThis` in development to avoid exhausting Postgres connections across Next.js hot reloads.
- `.env.example` — documents required env vars (`DATABASE_URL`, `DIRECT_URL`); real `.env` is gitignored.
- `prisma/migrations/` — versioned SQL migrations generated by `prisma migrate dev`, applied to the Supabase Postgres instance.

## Environment Variables

- `DATABASE_URL` — Supabase connection pooler (pgbouncer, port 6543) URL, used by the app at runtime.
- `DIRECT_URL` — Supabase direct connection (port 5432) URL, used by Prisma Migrate to run DDL (migrations require a non-pooled connection).

## Schema

Postgres tables/columns use `snake_case` (standard SQL convention); Prisma models/fields use `PascalCase`/`camelCase` (standard Prisma/JS convention), mapped via `@@map`/`@map`.

```prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider  = "postgresql"
  url       = env("DATABASE_URL")
  directUrl = env("DIRECT_URL")
}

model Blog {
  id          String     @id @default(uuid()) @db.Uuid
  url         String     @unique
  name        String
  author      String
  authorEmail String     @map("author_email")
  createdAt   DateTime   @default(now()) @map("created_at")
  updatedAt   DateTime   @updatedAt @map("updated_at")
  posts       BlogPost[]

  @@map("blogs")
}

model BlogPost {
  id        String   @id @default(uuid()) @db.Uuid
  blogId    String   @map("blog_id") @db.Uuid
  blog      Blog     @relation(fields: [blogId], references: [id], onDelete: Cascade)
  postTitle String   @map("post_title")
  url       String   @unique
  timestamp DateTime
  summary   String?
  thumbnail String?
  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @updatedAt @map("updated_at")

  @@map("blog_posts")
}
```

### Constraints

- `blogs.url` — unique.
- `blog_posts.url` — unique.
- `blog_posts.blog_id` — foreign key to `blogs.id`, `ON DELETE CASCADE` (deleting a blog removes its posts).
- Both tables get `id uuid` primary keys (`gen_random_uuid()` default via Prisma's `uuid()`), plus `created_at`/`updated_at` timestamps (`updated_at` auto-managed by Prisma on write).

`summary` and `thumbnail` are nullable (a post may not have either yet); all other fields listed by the user are required.

## Migration Workflow

1. Provision a Supabase project (or use an existing one); collect the pooled and direct connection strings.
2. Set `DATABASE_URL` and `DIRECT_URL` in `.env` (local) and in the deployment environment (App Engine `app.yaml`/secret manager, out of scope for this change — documented as a manual step).
3. Run `npx prisma migrate dev --name init_blogs` to generate the SQL migration and apply it to Supabase.
4. Run `npx prisma generate` to produce the typed client (also runs automatically via a `postinstall` hook).

## Verification

- `npx prisma migrate dev` completes without error against the Supabase database.
- `npx prisma studio` (or a throwaway API route) confirms both `blogs` and `blog_posts` tables exist with the expected columns and the FK relationship.
- `npx tsc --noEmit` passes with `lib/prisma.ts` and generated Prisma types in place.
